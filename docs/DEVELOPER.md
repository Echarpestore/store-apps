# دليل المطور — Echarpe / Glow Retail System

> لأي مطور هيشتغل على السيستم ده. اقرأه كامل قبل أي سطر كود.
> المرجع التشغيلي اليومي: `docs/OPERATIONS.md` · سجل الجلسات: `AI_HANDOFF.md`

## 1. نظرة عامة

منظومة ريتيل متكاملة self-hosted لسلسلة echarpe (3 فروع) + براند Glow:

| التطبيق | المسار | الوظيفة |
|---|---|---|
| POS | `pos/` | الكاشير: بيع، مخزون، تقارير، إقفال يوم، تحويلات بين الفروع، كروت موظفين |
| Sales/HR | `sales/` | حضور وانصراف، رصيد الوقت (الجزاءات)، المكافآت، البريك، الأذونات، المرتبات والسلف |
| Loyalty | `loyalty/` | تطبيق ولاء عملاء echarpe (نقط، مكافآت، push) |
| Glow | `glow/` | تطبيق ولاء Glow (أسود/دهبي) |
| Feedback | `feedback/` | تقييم العملاء |
| Functions | `functions/` | Cloud Functions: مكافأة الترحيب، عمولة الإحالة، إشعارات |

- **Stack:** Vanilla JS بدون build system. Firebase (Firestore + Auth + Functions + FCM).
- **SDK:** compat في POS/loyalty/glow/feedback · **modular** في sales.
- **الاستضافة:** GitHub Pages، رفع يدوي. الدومين: www.echarpe.store
- **الطباعة:** Electron wrapper بيعرّض `window.posShell.{listPrinters, printReceipt, printLabel, openDrawer}` + طابور طباعة سحابي (`pos_print_jobs`).

## 2. ⚠️ القاعدة الذهبية: الـ cross-block scope

**أكتر باج اتكرر في تاريخ المشروع.** الكود بيتوزع على أكتر من `<script>` block
(أو ملف). المتغيرات المعرّفة بـ `const/let` في module scope **مش بتشوفها**
الـ inline handlers في الـ HTML ولا البلوكات التانية → فشل صامت.

**القاعدة:** أي دالة أو متغير هيستخدمه HTML handler أو بلوك تاني →
عرّضه على `window` **بعد** تعريفه (مش قبله — TDZ crash):

```js
function approveReg(id){ ... }
window.approveReg = approveReg;   // ✅ بعد التعريف
```

اختبار `tests/test-sales-boot.js` بيتحقق من أهم التعريضات — لو شيلت واحدة
بالغلط الاختبار هيقع قبل ما الفرع يكتشفها.

## 3. هيكل ملفات POS

| ملف | مسؤوليته |
|---|---|
| `pos-core.js` | تسجيل الدخول (يدوي + سكان كارت)، الفرع، الأدوار |

| `app.js` | محررات تصميم الفاتورة/اللِبل، الاختصارات (F1-F8)، كاش الـ QR |
| `transfers.js` | التحويلات بين الفروع (تأكيد بشخصين — الناقل ميأكدش لنفسه) |
| `staff.js` | كروت الموظفين 5×9 (CODE128 بكود `EC` + 10 حروف) |
| `loyalty.js` / `discounts.js` / `profiles.js` / `products.js` / `search.js` / `import.js` | الولاء / الخصومات / ملف العميل / الكتالوج / البحث / الاستيراد |

تطبيق sales مقسوم: `index.html` (هيكل + CSS + watchdog) ·
`sales-app.js` (الموديول الرئيسي) · `sales-ui.js` (classic script).
**التقسيمة دي حرفية** — أي بلوك اتنقل لملف زي ما هو بالبايت. متلخبطش الترتيب:
الـ module deferred والـ classic بيتنفذ وقت الـ parse.

## 4. القرارات المحفورة (متتغيرش من غير قرار المالك)

- **10 دقايق تأخير = ساعة رصيد** (أقل من 10 = سماح يومي)
- **7 ساعات رصيد = يوم خصم من المرتب**
- **الرصيد المسموح شهريًا = 7 ساعات** — أول ما يوصله الموظف يخرج من المكافأة
  (متعمّد: "توصل ليوم خصم = برة المكافأة")
- **بوابة الالتزام 90% صلبة (hard gate)** — مش وزن. تحتها = خارج المكافأة
  مهما كانت المبيعات والتقييم. فوقها = 3 عوامل بأوزان 40/30/30
- **البريك الزايد متدرّج** زي التأخير (سد ثغرة "السماح الكبير")
- **أول تبديل شيفت في الشهر مجاني**، بعده بساعاته
- **عمولة الإحالة** بتتفعّل بعد **أول شراء حقيقي** بس (مش مجرد تحميل التطبيق)
- **التحويلات:** تأكيد استلام بكارت شخص تاني — الناقل ممنوع يأكد لنفسه
- **إقفال اليوم:** طلبات الموظفين بالمرتب داخلة الحساب · سلف الورق **مش**
  داخلة عهدة الدرج

## 5. الاختبارات

```
node tests/run.js
```

- بتشتغل على التقسيمة الجديدة أو الملف الموحد القديم تلقائيًا.
- `tests/helpers/dom-stubs.js` — بيئة DOM/Firebase وهمية (مؤقتات fake عشان
  متعلقش العملية).
- **قاعدة:** أي فيتشر جديدة في منطق حسابي (جزاءات/مكافآت/عمولات) لازم ليها
  اختبارات هنا **قبل** الرفع. وأي باج بيتصلح → اختبار بيثبت إنه مش هيرجع.

## 6. الأمان

- الـ rules في `security/firestore-phase2.rules` — **بتتنشر من Firebase Console
  يدويًا** (مش GitHub). `isStaff()` = حساب email/password، العملاء anonymous.
- قيود على مستوى الحقول (`hasOnly` / `diff`) — حافظ عليها في أي collection جديدة.
- **المرحلة 3 (معلّقة):** نقل حساب النقط والعمولات لـ Cloud Functions.
  لحد ما تتنفذ: أي كود client بيكتب نقط اعتبره مؤقت.
- `sales_app_referrals` كتابتها **function-only** — متفتحهاش للكلاينت أبدًا.

## 7. Cloud Functions

النشر من جهاز المالك: `cd echarpe-push && firebase deploy --only functions`
الدوال: `onRewardAdded` · `onCatalogUpdated` · `onWelcomeToken` · `onSaleForReferral`

## 8. إضافة فيتشر جديدة — checklist

1. اقرأ `AI_HANDOFF.md` (آخر حالة) + القسم 4 هنا (القرارات المحفورة)
2. فكّر في الثغرات الأول: إزاي موظف/عميل ممكن يستغلها؟ (تاريخ المشروع كله سد ثغرات)
3. اكتب المنطق الحسابي كدوال pure قابلة للاختبار
4. اختبارات في `tests/` → `node tests/run.js` أخضر
5. أي حاجة الـ HTML هيناديها → `window.X = X` بعد التعريف
6. bump الـ CACHE_NAME في `sw.js` بتاع التطبيق
7. ارفع دفعة واحدة → استنى العلامة الخضراء في Actions → افتح/اقفل مرتين
8. حدّث `AI_HANDOFF.md`
